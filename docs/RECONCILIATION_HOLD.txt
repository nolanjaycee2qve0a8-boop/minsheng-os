Atomic publication and races
Maintenance publishHold uses the SAME exclusive directory lock as the v1 journal,
verifies fixed inputs before and under lock, creates an exclusive pending marker,
fsyncs an exclusive staged envelope and links it atomically to a non-overwriting
final name. It verifies final bytes; only its own exact successful staging and
pending files are removed. A crash can leave lock/pending/staging; no automatic
repair, stale-lock deletion, journal reconstruction or refund is provided.
The deny-only production guard is in effect even BEFORE publication. There is no
allow decision to race with reservation. Ledger mutation is checked again under
the existing lock. The sidecar documents the incident; absence never authorizes.
This is tested process-interruption safety, not a claim of storage hardware
power-loss certification. Durability uncertainty also remains fail-closed.

Real installation preconditions

original hashes; confirm no active current sending workflow and no journal lock.
Then install only the sidecar with productionCase. If activity or identity cannot
be established, stop without installation. Never run authorization or approved
service commands as an installation test. Do not read a key. Installation outcome
and exact hashes belong in the D-drive acceptance report, not an invented RESERVE.
